# 2026/09/30 작업내용

카메라를 yaw/pitch 두 각도로 만들 때 문서에 "쿼터니언으로 마우스 회전을 누적하면 롤이 쌓여 지평선이 기운다"고 적어 뒀는데, 실제로 본 적은 없었다. 오늘은 새 기능 대신 이걸 재현해봤다. 재현은 됐고, 문서에 적어 둔 원인이 틀렸다는 것까지 확인.

## 진행한 작업

### 1. 재현 가능 여부 확인

- 엔진 카메라만으로는 재현 불가. `Camera::Rotate`가 yaw/pitch를 더한 뒤 `XMMatrixRotationRollPitchYaw(pitch, yaw, 0)`으로 행렬을 다시 만드는 각도 경로라 roll이 생길 자리가 없음.
- 대신 11-F에서 열어 둔 행렬 경로(`Camera::SetRotation`)가 있음. `CameraComponent`가 오브젝트 월드 행렬을 분해해 그대로 넘기므로, 스크립트가 오브젝트 회전에 roll을 섞으면 화면까지 도달한다.
- 11-F 이전이면 `CameraComponent`가 yaw/pitch 둘로 줄여 넘겨서 roll이 쌓여도 화면에 안 나타났을 것. 재현 도구가 없어서 버그가 없는 것처럼 보이던 상태.
- 결론: 행렬 경로는 이미 있으니 **쿼터니언을 누적하는 스크립트**만 만들면 됨.

### 2. 실험 전용 프로젝트 QuaternionLookTest

- 처음엔 Sample 프로젝트 `Scripts\`에 넣었다가 옮김. Sample 스크립트는 엔진 솔루션의 `SherlockEditor.exe`에 통째로 컴파일돼서 기본 에디터의 일부가 되고, 예제와 실험이 섞인다.
- 11-E 프로젝트 시스템으로 실험 전용 프로젝트 생성.

```
SherlockEditor.exe --new-project=QuaternionLookTest --exit-after=8
```

- `Projects\QuaternionLookTest\`에 `.sherlock`, `Assets\`, `Scripts\`, 에디터·게임 타깃 솔루션이 생김. 실험 스크립트는 이 프로젝트의 에디터(`Binaries\Debug\QuaternionLookTestEditor.exe`)에만 컴파일되므로 Sample 에디터에는 등록조차 안 됨.
- 실험용 스크립트는 `Scripts\` 바로 아래가 아니라 **`Scripts\Tests\`** 폴더에 모으기로 함. 폴더 이름만으로 게임용이 아니라는 게 드러나야 해서.
- 생성기가 뽑는 vcxproj가 `Scripts\*.cpp`만 컴파일하고 있어서 하위 폴더까지 잡도록 재귀 와일드카드로 변경. vcxproj를 손으로 고칠 일은 여전히 없음.

<!-- ProjectGenerator 가 만드는 vcxproj. 이전: Scripts\*.cpp -->

### 3. QuaternionLook 스크립트

- 위치: `Projects\QuaternionLookTest\Scripts\Tests\QuaternionLook.h/.cpp`
- 매 프레임 마우스 증분을 쿼터니언에 곱하고, 결과를 오브젝트 월드 회전으로 써 넣음.
- 마우스는 가상 마우스. 자동 검증은 창이 화면 밖이라 입력이 없고, 손으로 그린 원은 매번 달라 수치를 못 남긴다.
    1. (yaw, pitch) 평면에서 반지름 17°인 원을 120프레임에 한 바퀴
    2. 이웃한 두 점의 차가 그 프레임의 (Δyaw, Δpitch). 한 바퀴 합은 정확히 0
    3. 올바른 누적이면 매 바퀴 출발 자세로 돌아와야 함
    4. dt가 아니라 프레임 수로 진행하므로 결과가 매번 같음
- 증분을 **어느 공간에서 곱하느냐**를 `mode`로 나눔.

```cpp
// XMQuaternionMultiply(a, b) 는 "a 먼저, b 나중" (행벡터 행렬곱 a·b 와 같은 순서)
const XMVECTOR qPitch = XMQuaternionRotationAxis(XMVectorSet(1,0,0,0), dPitch);
const XMVECTOR qYaw   = XMQuaternionRotationAxis(XMVectorSet(0,1,0,0), dYaw);
if (mode == 0)
    q = XMQuaternionMultiply(XMQuaternionMultiply(qPitch, qYaw), q);   // 둘 다 자기(로컬) 축 → 6자유도식
else
    q = XMQuaternionMultiply(XMQuaternionMultiply(qPitch, q), qYaw);   // pitch 는 로컬 X, yaw 는 월드 Y → FPS 관례
q = XMQuaternionNormalize(q);
GetGameObject().SetWorldRotation(XMMatrixRotationQuaternion(q));
```

- mode 0: 두 증분 모두 카메라 자기 축. 6자유도 카메라 방식
- mode 1: yaw만 월드 Y축. 유니티·언리얼 FPS 컨트롤러 방식, `Camera::Rotate`와 같은 결과가 나와야 함
- 연결
    1. `Start`에서 자기 오브젝트의 `CameraComponent::priority`를 100으로(Main Camera는 0) → 활성 카메라
    2. (12, 4, −22)에서 (0, 2, 0)을 `LookAt`한 자세를 출발 쿼터니언으로
    3. 60프레임마다 자기 쿼터니언에서 역추출한 오일러와 `Camera::GetRoll`을 나란히 로그
- 씬 파일 둘. 데모 씬에 카메라 오브젝트를 얹어 `--add=4 --add-component=QuaternionLook --save=...`로 에디터가 저장한 `quat_roll_local.json`(mode 0), 그 사본의 `mode`만 1로 바꾼 `quat_roll_world.json`. `.sherlock`의 시작 씬은 첫 파일.

### 5. 원인은 부동소수점이 아니었다

- 문서에는 "부동소수점 오차로 미세한 롤이 쌓인다"고 적었는데 틀렸다. mode 1이 360프레임 동안 소수점 첫째 자리에서 0.0°였으니, 정규화된 쿼터니언을 360번 곱해서 생기는 오차는 그 정도도 안 됨.
- 진짜 원인은 **회전 합성이 교환법칙을 안 따른다는 것**.
    1. 두 증분을 모두 자기 축으로 곱하면, 마우스가 (yaw, pitch) 평면에서 닫힌 경로를 한 바퀴 돌 때마다 그 경로가 감싼 입체각만큼 roll이 남음
    2. 구면 위에서 벡터를 평행 이동시켜 제자리로 돌아오면 방향이 돌아가 있는 현상(홀로노미)과 같음
    3. 반지름 r인 원이면 한 바퀴에 2π(1 − cos r). r = 17°면 15.7°. 실측 15.2°와 거의 일치하고, 조금 작은 건 원이 아니라 120각형이라 넓이가 살짝 작아서
- 문서가 예로 든 `q = q_yaw · q · q_pitch` 꼴(yaw는 월드 Y, pitch는 로컬 X)은 매 프레임 결과가 Rx(p)·Ry(y) 형태를 유지해서 roll이 생길 수 없음.
- 정리하면 위험한 건 "쿼터니언"이 아니라 **증분을 어느 공간에서 곱하느냐**. 행렬로 누적해도 똑같이 생긴다. "yaw/pitch 두 각만 저장하면 이 부류의 버그가 원천적으로 안 생긴다"는 결론은 그대로 유효하고, 원인 문장만 틀렸던 것.
- mode 0의 roll은 6자유도 카메라에서는 버그가 아님. 위가 없는 우주선에선 그게 맞는 물리. FPS 카메라에서 버그가 되는 이유는 세계에 위(+Y)가 있어서고, 그래서 yaw는 월드 Y로 곱하거나 아예 각도 둘만 저장한다.
