# 2026/10/01 작업내용

RHI의 Handle 구조를 다시 검토. Concept은 덕 타이핑이라 다른 타입끼리 섞이는 걸 못 막을 것 같아서, Concept을 유지할지 인터페이스로 바꿀지 고민한 내용 정리.

## 진행한 작업

### 1. Handle의 역할

- Handle은 **GPU 리소스를 가리키는 번호표**. 렌더러는 `ID3D11Buffer` 같은 실제 객체를 들지 않고 `{index, generation}` 두 숫자만 들고 다님.
- 실제 객체는 백엔드 장치의 `ResourcePool` 안에 있음.

```cpp
BufferHandle vb = device->CreateBuffer(desc, data);   // 풀에 넣고 번호표를 받음
cmd->SetVertexBuffer(vb);                             // 번호표를 넘기면 백엔드가 풀에서 찾음
device->DestroyBuffer(vb);                            // 슬롯을 비우고 generation +1
```

- 맡은 일
    1. **그래픽 API 숨기기**: 핸들에 D3D 타입이 없어서 같은 렌더러 코드가 D3D11, D3D12 양쪽에서 그대로 돈다.
    2. **해제된 리소스 접근 잡기**: 슬롯이 재사용돼도 generation이 달라서 옛 핸들은 항상 `nullptr`. 포인터였으면 댕글링.
    3. **종류 섞임 방지**: `Tag`로 `BufferHandle`과 `TextureHandle`을 다른 타입으로 만듦.
    4. **값으로 다루기**: 8바이트라 복사, 비교, 해시가 쉽다. PSO 캐시 키에 셰이더 핸들이 그대로 들어감.
- 핸들 자체는 아무 동작도 안 하는 **키**. 백엔드별로 달라지는 동작은 `Device`, `CommandList`의 virtual 함수가 맡음.

### 2. 다른 타입끼리의 비교는 Tag가 막는다

```cpp
template <typename Tag>
struct Handle
{
    uint32_t index = UINT32_MAX;
    uint32_t generation = 0;

    bool IsValid() const { return index != UINT32_MAX && generation != 0; }
    auto operator<=>(const Handle&) const = default;
};

struct ShaderTag;
struct PipelineTag;
using ShaderHandle = Handle<ShaderTag>;
using PipelineHandle = Handle<PipelineTag>;
```

- `Tag`는 정의도 없는 빈 타입. 타입을 구분하는 용도로만 씀.
- `operator<=>(const Handle&)`는 **같은 Tag의 핸들만** 받음. 변환 생성자도 없음.
- 그래서 처음 걱정했던 "다른 타입끼리의 비교"는 원래부터 컴파일 에러였다.

| 코드 | 결과 |
|---|---|
| `shader == shader2` | 통과 |
| `shader == pipeline` | `C2679: binary '==': no operator found` |
| `shader < pipeline` | `C2679: binary '<': no operator found` |
| `shader = pipeline` | `C2679: binary '=': no operator found` |

- **Concept은 비교와 상관이 없다.** Concept은 템플릿 인자를 제약할 뿐이고, 비교가 되느냐는 `operator==` 오버로드가 정함.


### 3. C++20 이전 버전과 비교

- `Handle.h`를 C++20 적용 이전 형태로 되돌려 놓고 두 버전을 비교함.

| | C++20 버전 | 이전 버전 |
|---|---|---|
| 비교 | `<=>` default | 손으로 쓴 `==`, `!=` |
| 풀 제약 | `ResourceHandle` 콘셉트 | 없음 (`typename HandleT`) |

- C++20 버전
    1. 필드를 추가해도 비교가 자동으로 따라옴
    2. 순서 비교가 생겨 `std::map` 키로 쓸 수 있음
    3. 풀에 잘못된 타입을 넣으면 풀 본문이 아니라 **선언한 줄**에서 에러
    4. trivially copyable이 강제됨
    5. 단점: 콘셉트가 덕 타이핑, 의미 없는 `<` 비교가 열림, 헤더 의존이 늘어남
- 이전 버전
    1. 제일 단순하고 `<cstdint>`만 포함
    2. 동등 비교만 노출
    3. 단점: 비교를 손으로 유지해야 함, 풀에 제약이 없음, trivially copyable 보장이 주석뿐
- 두 버전 모두 교차 타입 비교는 막혀 있고 런타임 성능도 같다.
- C++20 버전을 쓰기로 함. 걸리는 건 덕 타이핑 하나였는데 이건 콘셉트를 쓰는 방식의 문제였다.

### 4. 콘셉트를 `Handle<Tag>` 특수화로

- 기존 콘셉트는 **모양**을 검사.

```cpp
template <typename T>
concept ResourceHandle = requires(const T h)
{
    { h.index } -> std::convertible_to<uint32_t>;
    { h.generation } -> std::convertible_to<uint32_t>;
    { h.IsValid() } -> std::same_as<bool>;
    requires std::is_trivially_copyable_v<T>;
};
```

- index, generation, IsValid()만 있으면 통과. 핸들과 상관없는 타입도 모양만 같으면 풀에 들어간다.

```cpp
struct EntityId { uint32_t index; uint32_t generation; bool IsValid() const; };

ResourcePool<D3D11Buffer, EntityId> pool;   // 통과함
```

- 핸들은 `Tag`로 **이름**을 보고 구분하는데, 풀의 제약만 **모양**을 보고 있었음.
- 조건을 "`Handle` 템플릿에서 나온 타입인가"로 변경.

```cpp
template <typename T>
inline constexpr bool kIsHandle = false;                  // 기본: 핸들이 아님
template <typename Tag>
inline constexpr bool kIsHandle<Handle<Tag>> = true; 

template <typename T>
concept ResourceHandle = kIsHandle<T> && std::is_trivially_copyable_v<T>;
```

- 동작
    1. `kIsHandle`은 모든 타입에 대해 `false`인 변수 템플릿
    2. 아래 줄은 그 **부분 특수화**. `T`가 `Handle<Tag>` 형태일 때만 컴파일러가 이쪽을 골라서 `true`
    3. `BufferHandle`은 `Handle<BufferTag>`이므로 `true`, `EntityId`나 `int`는 `false`
- 멤버를 보고 판단하면 구조적 타이핑(덕 타이핑), 어떤 템플릿에서 나왔는지로 판단하면 명목적 타이핑.
- **덕 타이핑은 Concept 자체의 성질이 아니라 `requires`로 멤버를 나열하는 방식에서 나온 것.** 조건식만 바꾸면 없어진다.
- `ResourcePool` 선언과 사용처 12곳은 그대로. `<concepts>` include는 필요 없어져서 뺌.

### 5. 확인

- 모양만 같은 구조체를 풀에 넣으면 선언 줄에서 에러.

```
concept_test.cpp(21): error C7602: 'ResourcePool': the associated constraints are not satisfied
ResourcePool.h(20): note: the concept 'ResourceHandle<LookAlike>' evaluated to false
```

- `static_assert`로 `BufferHandle`, `TextureHandle`, `ResourceSetHandle`은 통과, `LookAlike`, `int`, `const BufferHandle&`는 거부되는 것 확인.
- Debug, Release x64 빌드 경고 0, 오류 0.
- 에디터를 D3D11, D3D12로 각각 120프레임 실행, 둘 다 정상 종료.

### 6. 결론

- 다른 타입끼리의 비교를 막는 건 Concept이 아니라 **Tag**.
- 핸들은 인터페이스가 아니라 **값 타입**. 동적 추상화는 `Device`, `CommandList`의 몫.
- Concept이 덕 타이핑이 되는 건 쓰는 방식의 문제. **템플릿 특수화 여부로 조건을 걸면 명목적으로 쓸 수 있다.**
- `<=>`로 생긴 대소 비교는 아직 쓰는 곳이 없음. 맵 키로 쓸 일이 끝내 없으면 `==`만 default로 줄이는 것도 방법.
